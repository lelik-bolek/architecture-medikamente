# Стратегия комплексной защиты данных в покое и при передаче

Настоящий отчёт содержит техническую стратегию обеспечения информационной безопасности и комплаенса клиники «Медикаменте». Разработанное решение направлено на нейтрализацию угроз компрометации данных в трёх ключевых состояниях: в состоянии покоя (Data at Rest), в процессе передачи (Data in Transit) и в процессе использования (Data in Use).

Материалы отчёта структурированы в виде взаимосвязанных аналитических таблиц, декомпозирующих требования безопасности от бизнес-сущностей до физического оборудования:

1. **Таблица 1. Матрица классификации данных, профилей рисков и методов защиты.**
Связывает прикладные данные клиники с ключевыми угрозами и целевыми способами противодействия. В ней детализированы информационные активы организации, сформулированы риски нарушения их конфиденциальности и целостности, а также определены комплексные методы защиты.

2. **Таблица 2. Реестр аппаратных средств защиты данных (Hardware Security).**
Определяет перечень физических компонентов инфраструктуры, изолирующих среды вычислений и гарантирующих криптографическую стойкость на аппаратном уровне. Сюда включены самошифрующиеся диски (SED), криптографические модули (HSM/TPM), аппаратные сетевые экраны нового поколения (NGFW) и доверенные анклавы CPU (Intel SGX).


3. **Таблица 3. Реестр программных средств криптографической защиты (Software Security).**
Описывает платформенные сервисы, системное ПО и протоколы, реализующие защиту данных при хранении и сетевом взаимодействии. Раздел охватывает шлюзы API Gateway с принудительным шифрованием TLS 1.3 / mTLS, модуль управления секретами HashiCorp Vault, механизмы шифрования PostgreSQL (TDE/pgcrypto), централизованный сервис аутентификации Keycloak и интеграционный шлюз токенизации.


4. **Таблица 4. Реестр средств автоматизированного контроля за данными (Data Governance & Observability).**
Задает стек инструментов сквозного контроля и мониторинга данных. Включает платформу каталогизации и аудита Data Lineage (Apache Atlas), движок динамического разграничения доступа на базе тегов (Apache Ranger), оркестратор безопасных ETL-конвейеров и маскирования (Apache NiFi), а также централизованную систему мониторинга инцидентов и алертинга на базе OpenSearch/Prometheus.

## Таблица 1. Матрица классификации данных, профилей рисков и методов защиты.

| Данные | В чём необходимость защиты | Инструменты защиты |
| --- | --- | --- |
| **Персональные данные пациентов** (ФИО, дата рождения, контакты: телефон, email) | Риск компрометации персональных данных клиентов. | **Шифрование данных в покое:** AES-256 на уровне таблиц БД PostgreSQL. **Шифрование при передаче:** TLS 1.3 для Web, Mobile и API Gateway. **Защита в интерфейсах:** динамическое маскирование в UI регистратуры. |
| **Документы, удостоверяющие личность, и адреса** (сканы и реквизиты паспортов, полисов ОМС/ДМС, адреса регистрации) | Риск утечки персональных документов пациентов. | **Организационная мера (Data Minimization):** исключение сбора сканов и адресов при первичной записи. **Шифрование в покое:** AES-256 для файлов и S3-хранилища. **Контроль доступа:** списки ACL и ролевой доступ (RBAC) в IAM/Keycloak. |
| **Медицинские сведения и диагнозы** (анамнез, жалобы, диагнозы МКБ, протоколы приёмов, назначения) | Риск разглашения врачебной тайны и сведений о состоянии здоровья пациентов. | **Поколоночное шифрование в покое:** AES-256 клинических полей в PostgreSQL. **Контроль доступа:** модель ABAC/RBAC через Apache Ranger (только лечащему врачу). **Аудит доступа:** фиксация обращений к медицинским картам в Apache Atlas. |
| **Направления и результаты лабораторных исследований** (коды анализов, показатели биоматериалов, лабораторные протоколы) | Риск раскрытия медицинской тайны при передаче данных внешним контрагентам. | **Обфускация (токенизация):** замена ФИО на суррогатный `Token_ID`. **Защита каналов:** двусторонняя аутентификация mTLS и HTTPS REST API при обмене с лабораторией.|
| **Платежные и финансовые данные** (суммы чеков, кассовые проводки, транзакции, реквизиты оплат) | Риск нарушения конфиденциальности финансовых данных клиента. | **Токенизация эквайринга:** передача данных карт платёжному шлюзу банка без локального хранения. **Сетевая изоляция:** контур 1С изолирован от медицинских баз, обмен ведётся по защищённым портам/TLS. |
| **Юридические согласия пациентов** (статусы согласий на обработку ПДн, спецкатегорий и сервисных уведомлений) | Риск обработки персональных и медицинских данных без законных оснований либо после отзыва согласия субъектом. | **Целостность и неизменяемость:** хэширование записей и шифрование базы согласий AES-256. **Шина событий:** отправка сообщений об отзыве согласия для немедленной блокировки обработки профиля во всех модулях. |
| **Учётные данные сотрудников и ключи доступа** (логины, хэши паролей, сертификаты, сессионные токены JWT) | Риск несанкционированного доступа к управлению инфраструктурой, компрометации привилегированных учетных записей и перехвата сессий. | **Многофакторная аутентификация (MFA):** для врачей и администраторов. **Хранение секретов:** криптографическое хэширование паролей (Argon2), хранение ключей в HashiCorp Vault. **Безопасность сессий:** короткоживущие JWT-токены с проверкой на API Gateway. **Компрометация УЗ:** централизованная деактивация УЗ и отзыв сессий в Keycloak, применение короткоживущих JWT-токенов с проверкой на API Gateway.|
| **Аналитические и статистические выборки** (выгрузки P&L, ABC-анализ, когортная статистика для отчетов) | Риск косвенной деанонимизации пациентов по комбинации непрямых признаков и риск утечки внутренней коммерческой аналитики. | **Статическое маскирование и агрегация:** конвейер Apache NiFi удаляет PII, обобщает даты в возрастные группы и агрегирует диагнозы. **Сетевая изоляция:** доступ аналитика ограничен только витринами ClickHouse без доступа к транзакционным БД. |

## Таблица 2. Реестр аппаратных средств защиты данных (Hardware Security).

| Класс средства | Технология / Оборудование | Назначение и зона применения | Обеспечиваемое состояние |
| --- | --- | --- | --- |
| **Аппаратное шифрование накопителей**| **Самошифрующиеся диски (SED — Self-Encrypting Drives)** со стандартами Opal/Enterprise.| Серверные SSD/NVMe-диски СУБД (PostgreSQL, ClickHouse). Автоматическое аппаратное шифрование на уровне контроллера диска без падения производительности CPU сервера. Защита от физического хищения носителей.| **Data at Rest** (данные в покое).|
| **Аппаратные модули безопасности (HSM / TPM)**| **Аппаратный криптографический модуль (HSM / vHSM)** либо доверенный платформенный модуль **TPM 2.0** на серверах.| Аппаратная генерация, безопасное хранение мастер-ключей шифрования (Master Key) и закрытых ключей сертификатов TLS/mTLS. Исключает извлечение корневых ключей из оперативной памяти.| **Data at Rest / Data in Transit** (управление ключами).|
| **Сетевые аппаратные шлюзы безопасности**| **Межсетевой экран  (NGFW / Аппаратный фаервол)**.| Периметр локальной сети клиники. Сегментация сети на изолированные VLAN (контур медицинских БД, контур 1С/касс, публичный сегмент). Аппаратное терминальное завершение VPN-туннелей филиалов.| **Data in Transit** (данные в движении).|
| **Доверенные среды исполнения (Confidential Computing)**| **Аппаратные анклавы CPU (Intel SGX / AMD SEV)**.| Изоляция критических процессов обработки медицинских тайн и платежных транзакций в оперативной памяти. Предотвращение дампов памяти вредоносным ПО или привилегированными утилитами ОС.| **Data in Use** (данные в использовании).|

## Таблица 3. Реестр программных средств криптографической защиты (Software Security).

| Класс средства | Программный инструмент / Протокол | Назначение и зона применения | Обеспечиваемое состояние |
| --- | --- | --- | --- |
| **Шлюз безопасности и криптографический транспорт**| **API Gateway** с форсированием **TLS 1.3 / mTLS**.| Единая защищенная точка входа. Терминация публичного трафика с портала и мобильного приложения, обязательная двусторонняя аутентификация (mTLS) при обмене со шлюзом внешней лаборатории.| **Data in Transit** (данные в движении).|
| **Управление криптографическими ключами и секретами**| **HashiCorp Vault** (Key Management Service).| Централизованное хранение ключей шифрования БД, ротация паролей сервисов, выпуск динамических сертификатов и короткоживущих API-ключей.| **Data at Rest / Data in Transit**.|
| **СУБД-шифрование (Database Encryption)**| **Расширение pgcrypto / TDE (Transparent Data Encryption)** в PostgreSQL.| Поколоночное шифрование данных алгоритмом AES-256.| **Data at Rest** (данные в покое).|
| **Управление идентификацией и сессиями (IAM)**| **Keycloak** (OAuth 2.0 / OpenID Connect, Argon2id).| Централизованная аутентификация, строгий RBAC, форсирование MFA для врачей и администраторов, мгновенный отзыв сессий при подозрении на компрометацию.| **Data in Transit / In Use**.|
| **Шлюз токенизации и деперсонализации**| **Lab Integration Gateway / Token Vault** (на Java/Go).| Суррогатная замена персональных данных на `Token_ID` перед отправкой во внешние системы (лаборатория, эквайринг).| **Data in Transit / Data at Rest**.|

## Таблица 4. Реестр средств автоматизированного контроля за данными (Data Governance & Observability).

| Класс средства | Программный инструмент | Назначение в архитектуре «Медикаменте» |
| --- | --- | --- |
| **Каталогизация и сквозной аудит Data Lineage**| **Apache Atlas**| Автоматическое построение цепочки происхождения данных (откуда поступили, где трансформировались, куда переданы). Формирование аудиторского следа для подтверждения комплаенса по 152-ФЗ.|
| **Автоматизированный контроль политик на основе тегов (ABAC/TBAC)**| **Apache Ranger**| Динамическая блокировка запросов к колонкам с тегом `TAG:CONFIDENTIAL-PHI` для неавторизованных пользователей на уровне СУБД (PostgreSQL, ClickHouse). Автоматическое динамическое маскирование данных в реальном времени.|
| **Оркестрация безопасных потоков данных и статическое маскирование**| **Apache NiFi**| Автоматизированная очистка, обобщение (возрастные когорты, классы МКБ) и static data masking при репликации данных из операционного контура в аналитический DWH.|
| **Мониторинг событий безопасности и инцидентов (SIEM / Audit Logging)**| **Стек OpenSearch / ELK + Prometheus / VictoriaMetrics**| Сбор системных журналов доступа API Gateway и Keycloak. Автоматическое выявление аномальной активности (например, массовая выгрузка карт пациентов или многократные ошибки подбора пароля) и отправка алертов инженерам ИБ.|
