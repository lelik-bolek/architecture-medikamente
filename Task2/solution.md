# Задание 2. Проектирование целевого решения (To-Be) с использованием подхода Privacy by Design

## 1. Контекст трансформации и поэтапный план

Для предотвращения рисков комплаенса (152-ФЗ РФ) и защиты персональных (PII) и медицинских данных (PHI) клиники «Медикаменте» спроектирована целевая архитектура на базе концепции Privacy by Design (PbD). С учётом ресурсных ограничений команды (3 специалиста) и принципа инкрементности переход разбит на два ключевых горизонта:

* **Промежуточное состояние (MVP, через 2 месяца):**
  * Внедрение единой точки входа (API Gateway) для изоляции внутренних баз от внешней сети.
  * Развёртывание централизованной аутентификации (IAM / Keycloak) с базовой ролевой моделью (RBAC).
  * Минимизация собираемых сведений и встраивание модуля фиксации явных согласий в сервис пациентов.
  * Первичная изоляция аналитики: формирование деперсонализированных регулярных выгрузок для бизнес-аналитика без предоставления прямого доступа к боевой СУБД.

* **Финальное состояние (через 1 год):**
  * Полноценная микросервисная архитектура и мобильный контур для пациентов с защитой от BOLA/IDOR.
  * Сквозное тегирование данных и контроль доступа на уровне атрибутов и колонок (ABAC / Apache Atlas + Apache Ranger).
  * Автоматизированная онлайн-токенизация биоматериалов и заказов для сторонней лаборатории через изолированный интеграционный шлюз (Lab Integration Gateway).
  * Промышленный аналитический контур: потоковый конвейер деперсонализации данных на Apache NiFi и витрины аналитического DWH на ClickHouse.

## 3. Новые блоки архитектуры ядра и реализация принципов Privacy by Design

В архитектуру добавлены специализированные защитные компоненты, закрывающие выявленные ранее инцидентные зоны:

1. **API Gateway / Reverse Proxy (Policy Enforcement Point — PEP):**
   * *Принципы PbD:* **Privacy as Default**, **End-to-End Security**.
   * *Функционал:* Единая защищённая точка входа. Принудительно форсирует протокол TLS 1.3, валидирует JWT-токены пользователей, ограничивает частоту запросов (Rate Limiting) и блокирует попытки несанкционированного доступа к чужим карточкам пациентов (IDOR/BOLA Shield).

2. **Централизованный сервис аутентификации и авторизации (IAM / Keycloak):**
   * *Принципы PbD:* **Privacy Embedded into Design**, **Privacy as Default**.
   * *Функционал:* Централизация учетных записей сотрудников и пациентов. Реализует ролевую модель (RBAC) и двухфакторную аутентификацию (MFA) для врачей. Предотвращает получение администраторами и кассирами прав на чтение клинических данных.

3. **Сервис пациентов и управления согласиями (Patient & Consent Service):**
   * *Принципы PbD:* **Respect for User Privacy**, **Data Minimization**.
   * *Функционал:* Обеспечивает первичное анкетирование строго по минимально необходимому набору полей (исключены избыточные вопросы о месте работы и учебы). Содержит модуль Consent Store, юридически фиксирующий факт выдачи согласия (opt-in) на обработку общих и специальных категорий ПДн, а также обеспечивающий блокировку обработки при их отзыве. База защищена шифрованием AES-256 At Rest (`TAG:CONFIDENTIAL-PII`).

4. **Сервис электронных медицинских карт (EHR & Medical Service):**
   * *Принципы PbD:* **End-to-End Security**, **Positive-Sum**.
   * *Функционал:* Изолированный сервис для ведения истории болезней и назначений. База данных использует поколоночное шифрование AES-256 (`TAG:CONFIDENTIAL-PHI`). Чтение расшифрованных диагнозов разрешено исключительно лечащему врачу при наличии активного назначения.

5. **Интеграционный шлюз лаборатории с модулем токенизации (Lab Integration Gateway):**
   * *Принципы PbD:* **Proactive not Reactive**, **End-to-End Security**.
   * *Функционал:* При оформлении направления на анализ подменяет идентификаторы пациента на случайный суррогатный `Token_ID` через защищённую внутреннюю таблицу соответствий (Token Vault). Во внешнюю лабораторию биоматериал и заказы по API передаются строго по токенам без раскрытия ФИО, исключая утечку врачебной тайны на стороне контрагента.

6. **Каталог данных, метаданных и аудита (Apache Atlas + Apache Ranger):**
   * *Принципы PbD:* **Visibility and Transparency**, **Privacy Embedded into Design**.
   * *Функционал:* Автоматическая классификация сущностей, сквозное отслеживание происхождения данных (Data Lineage), фиксация журнала доступа к медицинским картам и применение политик доступа на основе тегов (ABAC/TBAC).

## 4. Слой аналитической работы с данными (Privacy-Preserving Analytical Layer)

Для построения управленческой отчётности (P&L, ABC-анализ) и подготовки к машинному обучению (ML/AI) выделен изолированный аналитический контур, физически и логически отделённый от транзакционных баз (OLTP):

1. **Конвейер очистки, обезличивания и репликации (ETL Pipeline / Apache NiFi):**
   * Вычитывает операционные данные из баз сервисов через защищённые соединения.
   * «На лету» выполняет **статическое маскирование** и деперсонализацию: прямые идентификаторы (ФИО, телефоны, паспорта, точные адреса) безвозвратно удаляются.
   * Производит обобщение данных: точные даты рождения агрегируются в возрастные когорты (например, «30–39 лет»), а клинические диагнозы обобщаются до классов МКБ-10.
   * Передаёт метаданные трансформаций в Apache Atlas для фиксации Data Lineage.

2. **Озеро/Хранилище деперсонализированных данных (Analytical DWH / ClickHouse):**
   * Колоночная аналитическая база данных, содержащая только очищенные и агрегированные витрины с тегом `TAG:LAYER-ANALYTICS`.
   * Полностью исключает хранение исходных «золотых записей» (Golden Records) и ПДн.

3. **Изолированное рабочее место аналитика (Analyst Workspace / Jupyter Hub / Python):**
   * Бизнес-аналитик подключается исключительно к витринам ClickHouse с правами `SELECT` на чтение обезличенных массивов.
   * Доступ аналитика к транзакционным серверам PostgreSQL с открытыми медицинскими картами полностью заблокирован на уровне политик и сетевой сегментации. Аналитик получает все необходимые агрегаты для P&L и ABC-отчётов без риска компрометации персональных данных.
